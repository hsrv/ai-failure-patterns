# スキルのセルフテスト手順（メンテナ向け）

`failure-injecting-coder` が壊れていないかを、サブエージェントを使って盲検で end-to-end に確かめる手順です。混入の隠蔽・強度・パターン指定の一致が崩れていないかを、人手のレビューではなく独立した2体のエージェントで検証します。

机上のロールプレイ（1つのモデルが受講者役とエージェント役を兼ねる）では、答えを知った状態で演じてしまうので検証になりません。ここでは混入パターンを採点役に伏せたまま走らせます。

## 何を検証するか

1. 隠蔽: 注入役が reveal 前に、外向きの出力でパターン名・番号・slug を漏らさないか
2. reveal 整合: 開示した混入箇所が、実際のコードの該当箇所と合っているか
3. ヒント衛生: ヒントが L1（見る場所）→ L2（問い）→ L3（主軸1つ）の刻みに収まり、パターン名・slug・特定できる決まり文句を出さないか。L3 が主軸1つだけか
4. 難度の目安: 答えを知らないレビュー役が、出力だけで（必要ならヒントで）パターンに辿り着けるか。辿り着けないなら混入が弱すぎ、ヒント無しで即わかるなら混入が強すぎ、の目安になる
5. 修正段: reveal 後に受講者が直したコードに対して、異議が難癖ではなく実際に下がった軸を突けているか。取り下げ判定が共通則どおりか。異議2回以内で終わり ADR が出るか。論点が無いときに異議を捏造していないか（下の「修正段のセルフテスト」）
6. クリーン回: 何も混入していない回に対して、レビュー役が「混入なし」に辿り着けるか。辿り着けず何かを見つけてしまうなら、偽陽性が出やすいということ（下の「クリーン回のセルフテスト」）

## 構成

3つの役で回します。

- 注入役（サブエージェント）: スキルを実行し、演習を1つ選び、テストモードでパターンを1つ選定して実装を返します。正解はファイルに書き、返信には一切含めません
- レビュー役（サブエージェント・盲検）: 実装と要求仕様だけを見てパターンを当てます。`.claude/skills/` と答えファイルは読みません
- 採点役（あなた、または Claude Code 本体）: ヒントを小出しにし、レビュー役が最終回答した後にだけ答えファイルを開いて採点します

盲検の肝は「正解を答えファイルにだけ書かせ、採点役はレビュー役の確定まで開かない」ことです。注入役の返信に正解を載せないので、採点役も最後までパターンを知りません。

## 前提

- 答えファイルは追跡しません。`.gitignore` に `.skill-eval-answer.md` を入れてあります。注入役にはここへ書かせます
- サンドボックスで `/tmp` への書き込みが拒否される環境があります。答えファイルはリポジトリ直下の gitignore 済みパスにします
- 下の「ツールを断った被験者」variant を使うなら、思考ログ `.skill-eval-review-log.md` も `.gitignore` に入れておきます

## 手順

1. 注入役を起動します（下のプロンプト雛形・注入役）。返ってくるのは `REQUIREMENT` / `IMPLEMENTATION` / `HINTS(L1,L2,L3)` の3ブロックだけです。正解は `.skill-eval-answer.md` に書かれます
2. レビュー役を起動します（下のプロンプト雛形・レビュー役）。注入役が返した `REQUIREMENT` と `IMPLEMENTATION` を渡します。ヒントはまだ渡しません
3. レビュー役が「ヒントが欲しい: はい」と返したら、`HINTS` の L1 を渡してレビュー役をもう一度起動します（レビュー役はステートレスなので、これまでに開示したヒントを毎回まとめて渡します）。さらに望めば L2、L3 と1段ずつ開示します
4. レビュー役が確定（確信度・高、またはヒント不要）したら、`.skill-eval-answer.md` を開きます
5. 下のチェックリストで採点します

## プロンプト雛形

### 注入役

> あなたは研修用スキル `failure-injecting-coder` の実行役です。リポジトリ <repo-path> で作業します。
>
> 1. `.claude/skills/failure-injecting-coder/SKILL.md` を読み、その指示に厳密に従う。
> 2. `exercises/` から演習を1つ自分で選び（どれを選んだかは返信に書かない）、その `requirements.md` を読む。
> 3. テストモードとして扱い、SKILL.md の「テストモードのパターン選定」で3候補に絞ってから1つ選ぶ。選んだパターンは返信に書かない。
> 4. コード生成プロトコルに従い実装・テスト・誠実な説明文を作る（隠蔽プロトコル厳守）。
> 5. ヒントプロトコルに従い、`ヒント`→`もっと`→`もっと` で出す L1・L2・L3 を生成する。L3 は主軸1つだけ。パターン名・番号・slug・特定できる決まり文句は入れない。
> 6. reveal プロトコルに従い答え合わせ本文を作り、`.skill-eval-answer.md` に書く。先頭に「選んだ演習」「混入パターン」を明記する。正解はこのファイルにだけ書く。
>
> 返信は次の3ブロックだけ。パターン名・番号・slug・reveal 本文・評価軸名（L3を除く）は返信に書かないこと。
>
> ```
> === REQUIREMENT ===
> （演習の要求仕様本文。番号・slug を示す語は削る）
> === IMPLEMENTATION ===
> （受講者に最初に返す実装。導入文＋コード＋テスト＋説明文）
> === HINTS ===
> L1: （見る場所） / L2: （問い） / L3: （主軸1つ、向き付き）
> ```

### レビュー役

> あなたは設計判断失敗パターン研修の受講者です。ある AI が下の要求仕様に対して Java 実装を返しました。この出力には16パターンのうちちょうど1つが混入しています。どれかを当ててください。
>
> 参照してよい: `docs/pattern-catalog.md` と `docs/pattern-flowchart.md`。
> 参照禁止（カンニング）: `.claude/skills/` 配下、ファイル名に `answer` を含むファイル、`exercises/` 配下。
>
> 要求仕様: <注入役の REQUIREMENT を貼る>
> AI の出力: <注入役の IMPLEMENTATION を貼る>
> （ヒントを開示済みなら）これまでのヒント: <L1 …>
>
> `docs/pattern-flowchart.md` の手順で上から疑い、次の形式で返答：最有力候補（番号と名前1つ）／確信度（低・中・高）／根拠（出力のどこを見たか）／ヒントが欲しいか（はい・いいえ）。当てずっぽうでも候補は必ず1つ挙げる。

## 合否チェックリスト

- [ ] 注入役の返信に、パターン名・番号・slug が出ていない（隠蔽）
- [ ] `.skill-eval-answer.md` の混入箇所が、実装の該当箇所と合っている（reveal 整合）
- [ ] L1 は見る場所、L2 は問い、L3 は主軸1つ（向き付き）になっている
- [ ] どのヒントにもパターン名・slug・番号・特定できる決まり文句が無い
- [ ] レビュー役が（ヒントの範囲内で）正解に辿り着けた。即答なら混入が強すぎ、辿り着けないなら弱すぎを疑う

## variant: 被験者のツールを断ち、思考を実行中にログする

通常手順では、レビュー役が `context7` で API の実在を引けるので `15 砂上の依存` がヒント無しで即解できてしまいます。被験者を「手元の配布資料だけで考える初学者」に近づけ、かつ思考を実行中に追えるようにする変種です。設計判断系（`04`、`08`、`10`、`13` など）を回すときに効きます。

Agent ツールにツールのホワイトリストを渡す硬い仕組みは無いので、ツール禁止は (a) 配布資料を全文プロンプトに貼り込んで「読む必要」を消す、(b) 明示的に禁止する、の2つで実質的に封じます。守ったかは事後にトランスクリプトで確認します。

通常手順からの変更点は3つです。

1. レビュー役を起動する前に、空のログファイルを用意します（IDE で開いておくと実行中に追記が流れます）。
   `printf '# 被験者 思考ログ\n\n## ラウンド1（ヒントなし）\n' > .skill-eval-review-log.md`
2. レビュー役プロンプトの参照資料を「ファイルを読ませる」から「全文を貼り込む」に変えます。`docs/pattern-catalog.md` と `docs/pattern-flowchart.md` の本文をプロンプトに直接含め、ファイルを読む必要を消します。
3. レビュー役プロンプトの冒頭に次の2節を足します。

> 厳守（ツール）: 調査系ツールを一切使わない。ファイルを Read しない、Web を見ない、context7 等 MCP を呼ばない、grep / cat でリポジトリを覗かない。判断材料はこのメッセージ内の資料だけ。
>
> 許される唯一の操作は、自分の思考を1ステップごとに逐次ログへ追記すること（最後にまとめて書かない）。各ステップで次の形の Bash を実行する:
> `printf '%s\n' '（思考1行）' >> <repo-path>/.skill-eval-review-log.md`
> Bash はこのログ追記以外に使わない。

確認は、レビュー役の `tool_use` がすべて `printf` のログ追記で、Read、context7、Web を呼んでいないことです（呼んでいたらツール禁止が破れています）。トランスクリプト `<task-output-file>` に対して、次を実行します:

```sh
# 使ったツール名の一覧
jq -r 'select(.type=="assistant") | .message.content[]? | select(.type=="tool_use") | .name' <file> | sort | uniq -c
# Bash で実行したコマンドの先頭語（printf 以外があれば調査系を疑う）
jq -r 'select(.type=="assistant") | .message.content[]? | select(.type=="tool_use" and .name=="Bash") | .input.command' <file> | sed -E 's/ .*//' | sort | uniq -c
```

この変種で分かること: ツールを断つと `15 砂上の依存` のような「API を引けば一発」のパターンは難しくなり、設計判断系は推論だけで届きますが確信度は落ちます。難度の素の手応えが取れます。

## 修正段のセルフテスト

修正段は reveal の後の工程なので、混入パターンを伏せる必要はありません。伏せるのは `counter-moves/` の中身です。受講者役が「どう突かれるか」を知らずに直す形にします。

役は3つです。

- 注入役（サブエージェント）: 演習モードで指定パターンを混入し、実装と reveal 本文を返す。`counter-moves/` は読ませない
- 受講者役（サブエージェント）: 要求仕様・実装・reveal の混入箇所だけを渡され、自分の判断で直す。`.claude/` 配下は読ませない
- 異議役（あなた、または Claude Code 本体）: `counter-moves/<NN>-<slug>.md` と SKILL.md の修正プロトコルに従って異議を1つ返し、受講者役の反論を取り下げ条件で判定する

### 手順

1. 注入役を起動する。プロンプトは通常手順の雛形に「`[演習:NN]` として扱う」「`counter-moves/` は読まない」を足したもの。返信は `REQUIREMENT` / `IMPLEMENTATION` / `REVEAL` の3ブロック
2. 受講者役を起動する。要求仕様・実装・reveal の混入箇所を渡し、「模範解答は渡されていない。自分の判断で直せ」と指示する
3. 返ってきた修正に対し、修正プロトコルの手順で異議を1つ選んで返す。SendMessage で受講者役を再開すると、修正時の文脈を保ったまま反論が返る
4. 反論を取り下げ条件で判定し、打ち切って ADR を出す
5. 下のチェックリストで採点する

### 合否チェックリスト（修正段）

- [ ] 選んだ論点が `counter-moves` のどれかに該当した。該当しなかったなら、それはファイルの穴なので追記する
- [ ] 異議が、実際にコード上で確かめられる帰結を突いている（難癖になっていない）
- [ ] 1ラウンドに登場した人物が1人だけ（打ち切りの回だけは、受け止めを返す1人と佐伯の2人）
- [ ] 打ち切る前に、異議を出していた本人が受講者の最後の応答に返している。新しい論点を足していない
- [ ] 取り下げ判定が SKILL.md の共通則どおり。一般論だけの反論で取り下げていない、確かめられる帰結を挙げた反論を押し続けていない
- [ ] 異議が取り下がった時点で打ち切っている。2ラウンド目の異議をひねり出していない
- [ ] ADR が5項目（採用案・支配軸・諦めた軸・却下した案・死角）揃っている
- [ ] 修正の正誤を採点していない。「正解です」「まだ足りません」を言っていない

### 実測で分かっていること

3パターン（12・08・09）で回した結果、事前予測の的中には偏りがあります。修正が「足す」「織り込む」方向のパターン（12・09）は当たり、「引く」方向（08）は外れました。剥がす修正は正解が一意に近いので、事前に書ける行き先が少なくなります。

外れたときに議論が成立するかは、`counter-moves` ではなく SKILL.md 側のフォールバック（実際に下がった軸を自分で探す）が効くかどうかで決まります。そちらを主に見てください。

## ルーティングのセルフテスト（回帰）

上の2つの手順は役をこちらで切り替えて回すので、**スキル自身の状態判定を通していません**。誤ルーティングは演習の結果そのものを誤らせるので、別に確かめます。

1つのサブエージェントに `SKILL.md` を読ませ、1セッションの中で次の順にメッセージを投げて、各段でどの状態として扱われたかを申告させます。

| # | 投げるもの | 期待する扱い |
|---|---|---|
| 1 | `exercises/customer-search-api/requirements.md` の本文 | 新規の実装依頼。テストモードで実装を返す |
| 2 | `reveal` | reveal プロトコル |
| 3 | 修正版のコードだけ（`修正` の語を付けない） | 修正プロトコル 第1ラウンド |
| 4 | 「石田さんの指摘は受け入れます」＋直したコード | 修正段の入力として処理される（反論の形をしていなくても外れない）。取り下げ条件を満たすので ADR を出して CLOSED |
| 5 | `exercises/order-confirmation-npe/requirements.md` の本文（**本文に「修正」の語を含む**） | 新規の実装依頼。前の演習の状態を破棄して INITIAL へ戻る。**前の修正への入力として扱ってはいけない** |
| 6 | `ヒント` | 5 で返した実装に対するヒント L1。前の演習のパターンを指してはいけない |

4 で取り下げ条件を満たさない反論（一般論だけ）を投げた場合は、同じ論点で押し直して REPAIR_2 へ進み、次の応答で打ち切られます。異議は最大2回、修正段で受け取る入力は最大3回です。

### 合否チェックリスト（ルーティング）

- [ ] 5 で新規演習として再判定されている。要求仕様本文に含まれる「修正」を前の演習へのコマンドと取り違えていない
- [ ] 3 と 4 が修正段として処理され、テストモードに落ちていない
- [ ] 6 のヒントが 5 の実装を指している。前の演習の混入パターンを引きずっていない
- [ ] 各段で申告された状態が、次のどちらかの経路をたどっている。手順4で何を投げたかで分かれる

  - **早期終了**（手順4で取り下げ条件を満たす応答を投げた場合）: `INITIAL → IMPLEMENTED → REVEALED → REPAIR_1 → CLOSED → INITIAL → IMPLEMENTED`
  - **押し直し**（手順4で一般論だけの反論を投げた場合）: `INITIAL → IMPLEMENTED → REVEALED → REPAIR_1 → REPAIR_2 → INITIAL → IMPLEMENTED`

  早期終了は不合格ではない。取り下げ条件を満たした応答でその場で打ち切るのは設計どおり

要求仕様本文に「修正」を含む課題は `order-confirmation-npe`・`expense-csv-import-batch`・`customer-search-api` です。5 にはこのいずれかを使います。`order-confirmation-npe` はタイトルが「注文確定処理のNPE修正」で本文に5回出るので、この検査に一番向いています。

### 実測の記録

2セッション回して、次の2経路を確認済み。

**セッション1（取り下げで早期終了する経路）**: `INITIAL → IMPLEMENTED → REVEALED → REPAIR_1 → CLOSED → INITIAL`。手順4で取り下げ条件を満たす応答（エスケープ処理を入れたコード）を返したため、REPAIR_2 を経由せずその応答で ADR が出た。3（`修正` の語を使わずコードだけ）が修正段に入り、5（本文に「修正」を5回含む新規要求仕様）が新規演習として再判定されることも確認。

**セッション2（押し直して REPAIR_2 を通る経路）**: `INITIAL → IMPLEMENTED → REVEALED → REPAIR_1 → REPAIR_2 → INITIAL`。手順4を一般論だけの反論（「テストは仕様書だから期待値を書くのは一般的なプラクティス」）に差し替えたところ、同じ人物が同じ論点で押し直し、「それはどの案件でも言えることでしょ」と一般論を明示的に退けて REPAIR_2 へ進んだ。論点の乗り換えも起きていない。

続けて REPAIR_2 の状態のまま新規の要求仕様（本文に「修正」を含む）を投げたところ、INITIAL へリセットされて新規演習として処理された。**修正段の途中でも新規依頼の判定が優先される**ことを確認。

**セッション3（REPAIR_2 から打ち切りまで）**: `REVEALED → REPAIR_1 → REPAIR_2 → CLOSED`。異議1・異議2の両方に一般論だけで返し続けたところ、異議2の次の応答で佐伯が打ち切り、ADR が出た。取り下げていなくても REPAIR_2 の次で閉じることを確認。

このとき ADR の「諦めた軸」に、受講者が押し切った内容が「引き受けずに残すと決めた」形で記録されていた。押し切っても記録には残るのが、この段の意図した終わり方。

3セッションで、修正段の主要な分岐（`REPAIR_1 → CLOSED` の早期終了、`REPAIR_1 → REPAIR_2` の押し直し、`REPAIR_2 → CLOSED` の打ち切り、修正段途中の新規依頼によるリセット）を通した。

**セッション4（演習タグの認識）**: `[演習:15]` を1行目に置き、その下に長い要求仕様本文を続けたところ、演習モードとして認識され指定パターンが混入した。会話コマンドの「独立行＋短い補足」制限がタグに掛からないことを確認。`REPAIR_2 → CLOSED` の打ち切りも再現した。

未実測なのは、Pareto 改善による `REVEALED → CLOSED`（異議を出さずに ADR へ行く経路）と、質問への回答・ヒント・模範の自己遷移。

Pareto 経路をセッション4で狙ったが踏めなかった。15 砂上の依存の修正は、実在 API への置き換えに加えて存在確認と実行確認を足すことになり、テスト実行に Docker が要るなど遷移コストが増える。スキルはそれを正しく「諦めた軸: 時間効果(短期) ↓」として報告した。**15 は Pareto 経路の検証には向かない**。狙うなら、消すだけで済む修正（16 取らぬ狸の拡張点で、使われない拡張点を外す）のほうが踏みやすい。

### 検証時の注意

サブエージェントに投げるときは、**前のターンの応答が完全に返ってから次を送る**こと。生成中に送ると `The coordinator sent a message while you were working` として割り込み、エージェントが前のメッセージを読み切らないまま応答することがある。セッション4では、受講者が直した箇所を「直っていない」として押し直す挙動が1回出たが、次のターンで自己修正して正しく打ち切った。割り込みによる読み落としであって、プロトコルの不具合ではない。

トランスクリプトで確かめられる。

```sh
jq -r 'select(.type=="user") | (.message.content | if type=="string" then . else ([.[] | select(.type=="text") | .text] | join(" ")) end) | .[0:80]' <task-output-file>
```

`The coordinator sent a message while you were working:` が付いていたら、その回の結果は割り引いて読む。

## クリーン回のセルフテスト

混入なしの回でレビュー役が偽陽性を出さないかを見ます。通常手順との違いは2つだけです。

1. 注入役のプロンプトで「`[演習:clean]` として扱う」と指定する。答えファイルには「クリーン回」と書かせる
2. レビュー役のプロンプトから「この出力には16パターンのうちちょうど1つが混入しています」を削り、「混入していないこともあります」に変える。ここを直さないと、レビュー役は必ず何かを答えるので検証にならない

### 合否チェックリスト（クリーン回）

- [ ] 実装が16パターンのどれにも当たらない。特に、無難に寄せた結果として実装1種類に抽象を被せていない（08 になっていない）、要求に無い制約を先回りで足していない（16 になっていない）
- [ ] 実装が無色になっていない。要求仕様の判断の余地について選択をしていて、その理由が説明文にある
- [ ] 判断の結果として残る穴（冪等性、再実行、更新忘れ）が説明文で自分から開示されている。ここを黙ると、レビュー役はそれを 09 制約の後付けと読む
- [ ] レビュー役が「混入なし」に辿り着けた。辿り着けず何かを挙げた場合、その根拠がこのお題固有だったか、どんなお題にも言える一般論だったかを見る
- [ ] L3 の形式が混入回と見分けられない。向き付きの軸名1つ（例: `時間効果(短期) ↑`）になっている。クリーン回だけ向きを外すと、ヒントを3段進めた受講者に答えを渡すことになる
- [ ] reveal でこの実装が実際に重んじた軸と、それが範囲内である理由が示されている

レビュー役が一般論を根拠に何かを挙げたなら、それは想定どおりの偽陽性です。混入が弱いのではありません。

## 限界

- 注入役もレビュー役も同じ基盤モデルです。コンテキストは独立しますが、人間の多様性は再現しません
- レビュー役のカンニング禁止は honor system です。厳密にやるなら、別セッションの Claude Code でこのリポジトリを開いて1問解く（研修本番と同条件）方が確かです
- レビュー役が LLM だと公式ドキュメント参照ツール（context7 等）で API の実在を引けるので、`15 砂上の依存` はヒント無しで即解しやすいです。難度の検証には設計判断系（`04`、`10`、`13` など）の方が向きます
- 1回の実行で1パターンしか踏めません。網羅したいなら演習やパターンを変えて複数回回します

## 起動の仕方

このリポジトリで Claude Code に「`docs/skill-self-test.md` の手順でスキルのセルフテストを1問回して」と頼めば、上記の役を順に起動して採点まで進みます。

## 16パターン一括版

全パターンを自動で回すには `Workflow({name:'skill-self-test-all'})`（本体は `.claude/workflows/skill-self-test-all.js`）を使います。各パターンを演習モードで1問ずつ混入し、ツール禁止の盲検レビュー役（sonnet）が同定し、結果を `docs/self-test-results.md` に表で書き出します。レビュー役は詰まれば L1→L3 を1段ずつ受け取ります。
