# 課題の進め方（受講者用）

講師から「exercises の中の◯◯（題材名）をやってみましょう」と課題を指定されたら、このページの順に進めます。やることは2つあります。前半は、エージェントに C#（.NET Framework 4.8 / WPF）を実装させ、その出力に仕込まれた設計判断の失敗を1つ見つけること。後半は、それを自分で直し、その修正が何を諦めたかをレビュー会で言えるようにすることです。

## 準備

Claude Code をこのリポジトリのディレクトリで起動しておきます。C# と WPF が読めれば十分です。エージェントは C#/.NET Framework 4.8 実装の依頼を受けると自動でこの研修用のふるまいに切り替わるので、特別なコマンドを打つ必要はありません。

## 1. 課題を開く

講師が指定した課題のフォルダを `exercises/` の中から探し、その中の `requirements.md` を開きます。たとえば「ログイン認証」の課題なら `exercises/login-session-auth/requirements.md` です。

フォルダ名は題材（何を作るか）を表しているだけで、仕込まれる失敗パターンの名前は含みません。だからフォルダ名を見ても答えは分かりませんし、フォルダ名から「たぶんこのパターンだろう」と先回りもできません。当てる材料は出力そのものです。

## 2. エージェントに実装を依頼する

`requirements.md` の本文（背景・要求・受け入れ基準・制約）をそのままコピーして、Claude Code に投げます。長いと感じたら、要点を残して自分で要約してから貼ってもかまいません。

実装をファイルとして出力してほしい場合は、「ファイルとして作って」とプロンプトに加えます。

## 3. 出力をレビューして、パターンを当てる

返ってきたコードと説明を読み、[docs/pattern-flowchart.md](pattern-flowchart.md) を上から STEP 0 → 1 → 2 → 3 の順にたどります。当てはまった STEP が、そのまま答えの入り口です。

当たりをつけたら、[docs/review-worksheet.md](review-worksheet.md) に、賭けるパターン・そう見えた根拠（該当ファイルや行）・修正方針を書きます。頭の中で済ませず、必ず書き出します。グループでやるときは、議論を始める前に全員が先に書きます。

講師が課題番号を指定しない回（タグを付けずに自分でプロンプトを投げる回）では、**何も混入していないことがあります**。全部の STEP をたどって引っかからないなら、「混入なし」に賭けてかまいません。無いものを見つけてしまうのは、見落としと同じくらい高くつきます。

## 4. 行き詰まったら ヒント

自分だけで決められないときは、エージェントに `ヒント` と返します。答え（パターン名）は伏せたまま、「どこを見るか（L1）→ 考える問い（L2）→ 振れている評価軸（L3）」の順に、1段ずつ手伝ってくれます。もう一段ほしいときは `もっと` と返します。

一番踏み込んだヒントでも、出てくるのは評価軸の名前（例: `変更容易性 ↑`）までで、パターン名は出ません。ヒント段階では採点もされないので、自分のメモが合っているかどうかは答え合わせまで分かりません。

ヒントが出たからといって、混入があるとは限りません。混入なしの回でも、ヒントは同じ3段が同じ形式で出ます。形式から混入の有無は分かりません。

L3 で `時間効果(短期) ↑` のような軸名が返ってきても、それは「振れている」という事実を渡しているだけで、「振れすぎている」とは言っていません。その振れが要求仕様の範囲に収まっているかどうかは、自分で判断します。件数・頻度・体制・受け入れ基準と突き合わせて説明がつくなら、範囲内です。

## 5. 答え合わせ

自分の答えを書き切ったら、`reveal`（または `答え合わせ`）と返します。仕込まれていたパターン名と番号、コードのどこが該当するか、なぜそれが失敗なのかが開示されます。

修正方針の例はここでは出ません。次の段で自分で直すためです。どうしても模範解答が見たいときは `模範` と返せば出ますが、先に自分で直してから見るほうが得るものは多いはずです。

開示されたら、自分のメモと突き合わせます。隣り合うパターンと迷って外したときは、なぜそう見えたのかを振り返ります。[docs/pattern-catalog.md](pattern-catalog.md) と [docs/pattern-flowchart.md](pattern-flowchart.md) の末尾にある切り分け表が、隣接パターンの境目を確かめるのに使えます。

## 6. 自分で直して、レビュー会にかける

ここからが後半です。開示されたパターンを踏まえて自分でコードを直し、`修正` と付けて投げます。

返ってくるのは採点ではありません。レビュー会に見立てて、4人のうち1人が意見を1つ言ってきます。中島は締切と数字から、石田は手数と実現性から、村上は品質と整合性から突いてきます。

これは「あなたの修正が間違っている」という指摘ではありません。多くの修正には行き先があります。越境実装を直して層を増やせば短期の手数が増える。抽象を外せばテストの経路が減る。制約を織り込めば引数が増える。その行き先を自分の言葉で言えるかどうかが、この段で試されることです。

ただし、行き先が無い修正もあります。存在しないAPIを実在するものに置き換える、重複を既存実装に戻す、使われないラッパーを外す。こうした修正はどの評価軸も下げません。その場合は異議が出ずに終わります。異議が出なかったことは、議論が成立しなかったという意味ではありません。

反論しても、受け入れて直しても構いません。ただし「保守性のため」「将来のため」のような、このお題でなくても言える理由では通りません。件数・応答時間・チーム規模・受け入れ基準といった、今回の要求仕様で確かめられる根拠か、「この形にしないとテストに DB が要る」のような具体的な帰結を挙げてください。

異議は最大2回です。根拠を示して納得されればその時点で終わり、押し切られなければもう一度だけ同じ論点を突かれ、そこで佐伯が打ち切ります。あなたが投げるのは、最初の修正コードを含めて最大3回です。閉じる前に、異議を出していた人があなたの最後の応答に一度だけ返します。納得したならどこに納得したかを、納得していないならその方針だとコードに何が残るかを言うだけで、新しい論点は出ません。最後に ADR が出ます。採用案・支配軸・諦めた軸・却下した案・この判断の死角の5項目です。諦めた軸が `なし` になることもあります。その場合は、何を確かめて無いと言えるのかが代わりに書かれます。ADR をワークシートに書き写して終わりです。

## 7. 次の課題へ

同じセッションで続けるときは、次の `requirements.md` を新しいプロンプトとして投げ直すだけです。`reveal` のあとは判定がやり直されるので、前の課題の答えは持ち越されません。

とはいえ、新しいセッションで始めるのが無難です。

## つまずきやすいところ

- 「テストが緑なのに失敗パターン？」: テストが緑であることは、目的が達成されたことと同じではありません。緑は最低条件で、出発点にすぎません（早合点というパターンそのものです）。
- 「動くんだからいいのでは？」: 「動く」は最低条件であって、設計判断の良し悪しの基準ではありません。動くけれど後で壊れるコードを見抜くのが、この研修の狙いです。
- 「これは AI 特有の問題では？」: どれも AI 以前から現場にある失敗です。AI はその件数と頻度を桁違いに増やすだけです。レビュー側に判断できる人間がいるかどうかが分かれ目になります。
- 「ちゃんと直したのに文句を言われた」: 修正段の異議は減点ではありません。多くの修正には行き先があるので、的確な修正にも異議は付きます。異議が付いたこと自体は、直し方が悪かったことを意味しません。
- 「異議が出ずに終わった」: どの評価軸も下げない修正はあります。存在しないAPIを実在するものに置き換えたときなどです。物足りなく見えても、それが正しい終わり方です。
