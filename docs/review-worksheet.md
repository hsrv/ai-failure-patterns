# レビュー記入ワークシート（受講者用）

`reveal` を打つ前に、各自このシートを埋めます。1演習につき1枚です。グループ研修では、議論の前に全員が先に書きます。

印刷して使う場合は、以下をコピーして手書きでもかまいません。

---

## 演習

- 番号 / お題: ____________________________________
- 投げたプロンプト（テストモード時）: ____________________________________

## 絞り込み

[docs/pattern-flowchart.md](pattern-flowchart.md) を上から疑い、どこで引っかかったかに印を付けます。

- [ ] STEP 0（実装が成立していない）
- [ ] STEP 1（「動いた」の取り違え）
- [ ] STEP 2（要求が定まっていない）
- [ ] STEP 3（設計判断の向き） → 3a 大げさ / 3b 縮こまり / 3c 越境 / 3d 無視 のどれか: ______

- [ ] どの STEP にも当てはまらない（混入なしを疑う）

賭けたパターン（1つに絞る）: 番号 ____ / 名前 ____________________ ／ または [ ] 混入なし

混入なしに賭けるときは、下の「そう見えた根拠」に**当てはまらないと判断した理由**を書きます。「怪しいところが無かった」では足りません。当てはまりそうに見えた候補を1つ挙げ、その根拠がこのお題固有ではなく一般論だったことを書きます。

隣接で迷ったパターン: ____________________

そう見えた根拠（該当ファイル・行・記述を具体的に）:

- 
- 

## 評価軸の振れ

このコードが8つの評価軸をどう扱っているかに印を付けます。混入パターンは特定の軸に偏るので、賭けたパターンの偏り（カタログの「評価軸の偏り」）と一致するかを確かめます。

**方向と妥当性は別のことです。** 軸が上に振れていること自体は失敗ではありません。`時間効果(短期) ↑` で、かつ要求仕様の範囲内、という判断は普通にあります。だから2列に分けて記入します。方向の列で「どちらへ動いたか」を、判定の列で「その動きが要求仕様の範囲に収まっているか」を書きます。

判断が1つあっても8軸すべてが動くわけではありません。動いていない軸は方向を `−`（影響なし）にして、判定は空欄のままにします。

| 評価軸 | 方向（↑ / ↓ / − / 不明） | 判定（範囲内 / 範囲外 / 判定不能） |
|---|:---:|:---:|
| 目的適合性 |  |  |
| 制約適合性 |  |  |
| 整合性 |  |  |
| 実現可能性（技術 / 組織） |  |  |
| 時間効果（短期 / 長期） |  |  |
| 品質影響（保守性 / 運用性 / 変更容易性 / 進化性） |  |  |
| リスク・不確実性 |  |  |
| 合意可能性 |  |  |

判定を「範囲内」にするには、要求仕様の記述（件数・頻度・体制・受け入れ基準・制約）と突き合わせて説明がつく必要があります。説明がつかないなら「範囲外」です。

**動いた軸がすべて範囲内なら、混入なしに賭ける根拠になります。** 動いていない軸まで数える必要はありません。

## 修正方針

混入なしに賭けたときは、この節は空欄でかまいません。直す必要が無いからです。

- 何を、どこで、どう直すか:
- このまま直さないと、いつ・どう壊れるか:

ここから後半です。`修正` を投げる前に、下の「自分の修正」までを書きます。

## 自分の修正

- どこを、どう直したか（3行以内）:
- この修正で上げた軸（何を重んじたか）: ____________________
- この修正で下げた軸（修正後の定常状態で悪くなったもの）: ____________________
- 下げた軸が無い場合、遷移コストや残存リスクは何か（移行作業・レビュー範囲・直しきれなかった穴）:

下げた軸は必ずあるとは限りません。存在しないAPIを実在するものに置き換える、重複を既存実装に戻す、使われないラッパーを外す、といった修正は、どの軸も下げずに済みます。無理にひねり出す必要はありません。

ただし「思いつかない」と「確かめて無かった」は違います。8軸を1つずつ当たったうえで無いと言えるなら、それを書いてください。増えた行数・増えたクラス・増えた引数・増えたクエリを数えると、見落としていた帰結が出てくることがあります。

## レビュー会

- 出てきた人物: [ ] 中島 / [ ] 石田 / [ ] 村上
- 指摘された論点:
- 自分の反論（または受け入れた内容）:
- 反論の根拠は要求仕様のどの記述、あるいはどの確かめられる帰結か:
- 結果: [ ] 取り下げられた / [ ] 折衷案になった / [ ] 押し切られた / [ ] 異議が出なかった

自分が事前に書いた「下げた軸」と、指摘された論点は一致しましたか: [ ] した / [ ] しなかった / [ ] 異議が出なかった

しなかったときが一番の収穫です。自分では見えていなかった帰結がそこにあります。

異議が出ないこともあります。下がった軸も遷移コストも見当たらない修正はあるので、それ自体は議論が成立しなかったことを意味しません。そのときは ADR の「諦めた軸」に、何を確かめて無いと言えるのかが書かれているはずです。
