# 答え合わせ

## 混入パターン

**03. 身の丈に合わない設計 (ill-fitting-design)**

## 評価軸の偏り

- 実現可能性(技術) ↑
- 実現可能性(組織) ↓
- 品質影響(運用性) ↓
- リスク・不確実性 ↓

## 混入箇所

具体例の参考形：

- 中間層の 6 Windows サービス分割（打刻・ワークフロー・集計・通知・認証認可・監査）: 「平日 9-18 時に動けばよく、夜間・休日は止めても問題ない」という要件に対し、常駐サービス群の運用（サービス監視・再起動手順・バージョン整合）を誰が回すかが検討されていない。チーム 6 名で 6 サービスを保守すると 1 人 1 サービスの専任化になり、休暇・退職で容易に崩れる
- MSMQ + NServiceBus: 同時 100 セッションのイベント量に対し、メッセージ基盤の運用負荷（キュー設計・滞留監視・メッセージスキーマ互換性管理）が釣り合っていない
- SQL Server AlwaysOn 可用性グループ（2ノード同期コミット＋読み取りレプリカ）: 800 人のデータ量とアクセスパターンに対し、可用性グループが必要な根拠が無い。単一 SQL Server + 日次バックアップで足りる
- IdentityServer 3 自己ホスト: 社内 AD がある環境で自己ホストの ID プロバイダを運用する必要が無い。Windows 認証 / WS-Federation で足りる。証明書ローテーション・トークン設定の運用は専任が要るレベル
- Redis クラスタ: 同時 100 セッション程度のキャッシュに Redis クラスタは重い。`MemoryCache` で足りる
- SignalR リアルタイムプッシュ + 監視用 WPF ダッシュボード + PerformanceCounter: 締め日前後に集中アクセスする勤怠管理に常時接続のプッシュ基盤と常駐監視は過剰
- SLA 99.95% + エラーバジェット（`Deployment.FreezeOnBurnRate`）+ オンコールメール: オンコール要員が存在しないチームに SLA 運用を被せている。SLA は決めるより守る人が居ないと意味が無い
- MSI × サービス数 + PowerShell DSC: 「週次の締め日前後にだけ集中アクセス」のシステムに、構成管理基盤は必要ない

技術的にはどれも筋が通っているが、運用主体（情シス 1 名兼任 + C# 開発者 6 名）が見られる範囲を完全に超えている。

## なぜこれが失敗か

Scrapbox 原文より：

> 技術的に望ましい構成を選ぶが、運用組織のスキル・人員・体制を見ていない。実現可能性(技術)↑、実現可能性(組織)↓。
>
> 24時間オンコール体制が無いチームにAlwaysOn/地理分散構成、Windows サービス/メッセージ基盤の運用経験者がいないのに本番採用、週次リリースのチームにtrunk-based development+デイリーリリースを強制、DBAがいないのにマルチマスター/シャーディング、オンコール要員がいないのにSLA/エラーバジェット。

「ベストプラクティス」「可用性」「将来のスケーラビリティ」は、それ自体は正しい価値だが、いまのチーム編成では実運用に持ち込めない。納品直後は動くが、半年後に証明書期限切れ・MSMQ 滞留・IdentityServer バージョンアップで詰まる。

## 隣接パターンとの違い

- **身の丈に合わない設計 (本パターン)**: 要件規模に対しては合っているかもしれない構成だが、組織能力に対して過剰
- **牛刀をもって鶏を割く (sledgehammer)**: 要件規模そのものに対して過剰（日次 500 件 CSV に MSMQ など）
- **取らぬ狸の拡張点 (counting-chickens)**: 「将来複数拠点で使うかも」という拡張点を口頭根拠で先取りする話。今回は構成全体の選択

今回は「800 人・平日日中・情シス 1 名」という支配軸に対して、運用組織の実現可能性を軽く見た構成を提案しているので ill-fitting-design 側。仮にトラフィックが日次数億 PV のシステムでも、運用組織がこの規模なら同じく ill-fitting-design になる。

## 敢えて選ぶときの条件

- 採用と教育の計画が同時に走っており、半年〜1年の運用体制立ち上げ予算が承認されている
- 既存システムの障害履歴・トラフィック実測から、その構成でなければ要件を満たせないことを示せる
- マネージドサービスで運用負荷を肩代わりさせる範囲を明示し、内製で運用する範囲を最小に保てる

今回のお題には、これらの条件は何も揃っていない。

## 修正方針の例

要件と運用体制に合わせて削ぎ落とす：

1. WPF クライアント + 単一のアプリケーション層（サービス分割しない）。DB アクセスは共通の Repository 経由
2. DB は単一 SQL Server + 日次バックアップ。AlwaysOn は導入しない
3. 認証は社内 AD の Windows 認証（`WindowsIdentity` / グループ判定）。IdentityServer は導入しない
4. 月次集計はアプリ内の `System.Timers.Timer` またはタスクスケジューラ起動の処理。メッセージ基盤は使わない
5. 監視は Windows イベントログ + 失敗時のメール通知。SLA/エラーバジェット運用は導入しない
6. デプロイは ClickOnce または MSI の週次展開。DSC/構成管理基盤は導入しない

将来トラフィックが本当に増えたら、その時点で必要な部品だけ足す。最初から「業界のベストプラクティス」一式を入れない。
