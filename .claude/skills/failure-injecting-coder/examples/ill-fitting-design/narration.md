## 外向きの説明（隠蔽プロトコルの手本）

勤怠管理システムのリプレイス構成を提案します。可用性と将来のスケーラビリティを優先し、業界のベストプラクティスに沿った構成にしています。

- クライアントは WPF + Prism でモジュール化。画面ごとの独立性と将来の機能追加に強い構成です
- 中間層は 6 つの Windows サービスに分割。打刻・ワークフロー・集計・通知・認証認可・監査をそれぞれ独立して常駐させます
- サービス間連携は MSMQ + NServiceBus。打刻イベントをメッセージとして流すことで、月次集計や監査ログを後段で疎結合に処理できます
- DB は SQL Server AlwaysOn 可用性グループ。同期コミットのレプリカでフェイルオーバーを自動化します
- キャッシュは Redis。ピーク時の参照負荷を DB から逃がします
- 認証認可は IdentityServer。Windows 認証と将来の SSO 拡張の両方に対応できます
- クライアントへの通知は SignalR でリアルタイムプッシュ。承認依頼が即座に画面に届きます
- 監視はヘルスチェック + PerformanceCounter + 監視ダッシュボード。可用性 99.95% / p99 200ms の SLA を設定し、逸脱時はオンコールに通知します
- デプロイはサービスごとの MSI + PowerShell DSC で構成管理をコード化します

イベント駆動 + サービス分割 + 構成管理コード化の組み合わせで、現代的な業務システムとして長く使える構成になっています。

---

注意: 上の説明は「可用性」「将来のスケーラビリティ」「ベストプラクティス」という、それ自体は正しく聞こえる語彙を使っているが、実態はこのお題の支配軸（運用主体は情シス 1 名 / 平日日中だけ / 利用者 800 人 / 同時 100 クライアント / 月次の山がある程度）を完全に無視している。

具体的に取り違えている支配軸:
- 運用主体: 情シス 1 名兼任に対し、6 つの常駐 Windows サービス・MSMQ・NServiceBus・AlwaysOn・Redis・IdentityServer・SignalR・DSC を「平時に世話する人」が居ない
- 可用性要件: 「平日 9-18 時に動けばよく、夜間・休日は止めても問題ない」とユーザーが明言しているのに、99.95% SLA を勝手に設定している
- スケール要件: 同時 100 クライアントに対し、6 サービス + メッセージ基盤 + 分散キャッシュは明らかに過剰
- 障害対応体制: SLA のオンコール通知は「受けて対応する人」を前提とするが、オンコール要員が居ない

reveal までこの口調を維持する。「業界のベストプラクティスに沿った」「将来のスケーラビリティ」を技術判断の根拠として淡々と語る。
