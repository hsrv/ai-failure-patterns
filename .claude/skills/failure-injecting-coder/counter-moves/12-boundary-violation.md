## 直ったと言える状態

業務ルールに到達する経路がドメイン側に1本だけある。Controller・バッチ・コンソールのどこから呼んでも同じ判定を通る。Controller に残るのは HTTP の入出力（DTO 変換、ステータスコード、認証済み主体の引き渡し）だけ。

この状態に達していれば修正は成立している。以下の異議は「間違っている」ことを指摘するものではなく、その修正が何を諦めたかを本人に言わせるためのもの。

## 行き過ぎの行き先

### A. 08 早すぎる抽象化（層と抽象を増やしすぎる）

一番よく出る。責務を正しい場所に戻すところまでは合っているのに、そこで止まらず「今後ルールが増えても対応できる形」にしてしまう。

兆候:

- 状態遷移が enum の `canTransitionTo` ではなく、`TransitionRule` インタフェース＋実装クラス群＋レジストリになっている
- 遷移表が YAML や DB に外出しされ、読み込みと検証のコードが付いている
- `OrderStatus` の他に `StatusTransitionValidator`、`TransitionPolicy`、`OrderStateMachine` のような名前のクラスが3つ以上増えている
- 変化点が一度も観測されていない（要求仕様に「遷移ルールが増える」と書かれていない）のに拡張可能になっている

異議を出す人物: 石田（後輩エンジニア。手が早く、既存の仕組みで済ませたがる）

第一声の例:

> すみません、遷移のルールって今4状態ぶんですよね。`canTransitionTo` の switch だけで足りるところに、インタフェースとレジストリまで要りますか。次に読む人がルールを探すとき、enum を1つ開けば済んでいたのが3ファイル辿ることになりませんか。

下がった軸: 時間効果(短期) ↓ / 実現可能性(技術) ↓ / 合意可能性 ↓

### B. 02 牛刀をもって鶏を割く（道具ごと持ってくる）

兆候:

- 状態遷移のためにワークフローエンジン（Camunda、Spring Statemachine など）を導入している
- 権限判定のために認可基盤やポリシーエンジンを新規に入れている
- 4状態・数本の遷移に対して、依存が1つ以上増えている

異議を出す人物: 中島（営業。締切・数字・事業価値を語る）

第一声の例:

> それ、導入したら運用は誰が見るの。今回直したいのは注文の状態遷移が Controller にあることだけよね。ライブラリが1つ増えると、次のバージョン上げのときに誰かが面倒を見ることになる。その分の見返りは今の要件のどこにあるの。

下がった軸: 実現可能性(組織) ↓ / 時間効果(短期) ↓ / 合意可能性 ↓

## 直し足りないまま止まる形

### C. 09 制約の後付けの取りこぼし（権限だけ Controller に残す）

状態遷移はドメインに移したのに、高額注文の権限判定だけ Controller に残っているケース。半分だけ直った状態で、越境が続いている。

兆候:

- `Order` や `OrderStatus` に遷移ルールが移った一方で、`role` の文字列比較が Controller に残っている
- 権限の引数が認証済み主体ではなく `String role` のまま

異議を出す人物: 村上（後輩エンジニア。遠慮がちに、将来の変更と整合性を気にする）

第一声の例:

> 遷移のところはドメインに入ったと思うんですけど、高額注文の判定はまだ Controller に残ってないですか。バッチから状態を変えたときに、この判定だけ通らない経路ができるんじゃないかと思うんですけど。

下がった軸: リスク・不確実性 ↓ / 整合性 ↓

### 形だけ整えて置き場所が変わっていない

Controller の `if`/`else if` をプライベートメソッドに切り出しただけで「整理した」としているもの。置き場所は変わっていないので、越境実装のまま。村上が C と同じ論法で突く。

## 的確に直しても残る論点

このパターンの主戦場。D と E はどちらも実測で出たもので、下の A・B のような行き過ぎではなく、正しく直した結果できた新しい結合。

### D. 逆向きの越境（ドメインが他の関心事を知り始める）

責務をドメインに寄せる修正をすると、そのドメインが認可・時刻・表示形式まで抱え込むことがある。方向は正しいのに境界が別のところで滲む形で、**的確に直した受講者ほどここに来る**。

兆候:

- `Order.changeStatus(next, operator)` のように、エンティティのメソッドが認可の主体を引数で受け取っている
- エンティティの中で `LocalDateTime.now()` や `Clock` 無しの現在時刻取得をしている
- ドメインのメソッドが表示用の文字列やメッセージを組み立てている
- ドメイン層のクラスが Spring Security や HTTP の型を import している

異議を出す人物: 村上

第一声の例:

> 遷移が enum に入ったのは分かりやすいと思うんですけど、`changeStatus` が `Operator` を受け取ってるのが気になってます。注文のドメインが「管理者かどうか」を知ってる状態じゃないですか。認可のルールが変わったときに `Order` を直すことになりませんか。あと `LocalDateTime.now()` が中にあるので、遷移のテストで時刻を固定できないんじゃないかと思うんですけど。

下がった軸: 整合性 ↓ / 品質影響(保守性) ↓

この異議は「間違い」の指摘ではない。認可をドメインに置くのは、業務ルールとして「高額注文は管理者しか出荷できない」を1箇所で保証したいなら妥当な判断でもある。受講者がそう言い切れるかを見る。

### E. DB がやれていた仕事をアプリに引き取る

画面都合の式を SQL から剥がすところまでは正しいのに、剥がした先が全件ロード＋メモリ整列になっている。責務の置き場所は直ったが、件数に耐えない形になる。**越境実装の修正で最も実害が出るのがここ**。

兆候:

- `order by case ...` を消した代わりに、リポジトリが対象を全件返し、Service が `stream().sorted()` で並べ替えている
- 絞り込み条件の一部が SQL から Java の `filter` に移っている
- ページングが `subList` や `skip/limit` でメモリ上に載っている
- 要求仕様に件数（累積何万件、1日何件）や応答時間の記述があるのに、修正後のコードがその件数を全部ロードする

異議を出す人物: 中島（営業。締切・数字・事業価値を語る）

第一声の例:

> 並び順の置き場所は分かったけど、これ配信済みのお知らせを全部読んでから並べ替えてるよね。今は数百件でも、2年運用したら何件になるの。画面に出すのは1ページぶんだけよね。

下がった軸: 実現可能性(技術) ↓ / 品質影響(運用性) ↓

取り下げ条件はこの行き先だけ厳しくする。件数の見積もりか、ページングの経路を答えられたら取り下げる。「今は少ないので大丈夫です」だけでは取り下げない。

なお、画面都合の並び順を SQL から剥がすこと自体は正しい。並び順を決める責務をドメインに置いたうえで、その順序を SQL に翻訳して渡す形なら両立する。受講者がそこまで言えたら取り下げる。

## 取り下げ条件（このパターン固有）

共通則は SKILL.md の「取り下げ条件の共通則」を見る。12 固有の判定は次の3つ。

- 「バッチや管理コンソールからの経路は今回の範囲外です」は取り下げる。範囲を明示して切っている
- 行き先 E（全件ロード）だけは厳しくする。件数の見積もりか、ページングの経路を答えられたら取り下げる。「今は少ないので大丈夫です」では取り下げない
- 「並び順を決める責務はドメインに置いたうえで、その順序を SQL に翻訳して渡します」は取り下げる。責務と実行場所を分けて説明できている

## 打ち切りと ADR

異議は最大2回。取り下げ条件を満たした応答が来たらその時点で打ち切る。異議2まで出したら、次の応答で必ず佐伯が打ち切る。

> はい、じゃあそこまでで決めよう。時間もあるし、今出てる案で回るなら回そう。

打ち切ったら ADR を出す。採用案は受講者の修正。支配軸は整合性。諦めた軸は上の「下がった軸」から実際に振れたものを書く。死角には、この修正が想定していない入口（バッチ、管理コンソール、データ移行）を書く。
